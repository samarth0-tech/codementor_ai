# ADR 0005: AI code review of submissions

- Status: Accepted
- Date: 2026-10-15

## Context

After a student submits code, the platform should explain what is good, what may be wrong, how to
improve it, and the time and space complexity. The review is generated by an AI, so it can be wrong,
manipulated by the code it reads, expensive, and, if built carelessly, a way to leak hidden test data.
It must also keep working whichever code executor is in use (Judge0, Piston, the simulated one).

## Decision

1. **Reuse the AI architecture from ADR 0002.** The review goes through `AiService.generateStructured`
   (provider interface, Zod-validated output with one repair attempt, retries, timeouts, daily quota,
   audit row in `AiCall`). No new AI plumbing, no new environment variables.
2. **The AI rates and writes; the application calculates.** The AI gives three ratings from 0 to 10
   (correctness, readability, maintainability) and text. The overall score is computed by
   `computeOverallQuality` (50/25/25) in `packages/shared`. Extra fields such as a self-assigned score
   are dropped by the schema.
3. **The real test result limits the correctness rating** (`limitCorrectness`): code that did not
   compile cannot score above 2, runtime errors 4, time/memory limits 5, wrong answers 3 to 6 depending
   on how many tests passed, and code that passed everything gets at least 6. The AI cannot talk its way
   past evidence from really running the code, and the UI says when this adjustment happened.
4. **Hidden test data never enters the prompt.** The AI is given the problem statement, the code, the
   verdict, pass counts, compiler output and the failing EXAMPLE tests only; hidden tests contribute
   counts and nothing else. Otherwise the AI could quote them in its review and leak them to the
   student. `buildContext` and `buildReviewPrompt` are the only code that decides this, and tests assert
   that planted hidden markers never reach the prompt or the response.
5. **Student code is untrusted data.** It is wrapped in `<student_code>` tags with any attempt to close
   the tag removed, and the system prompt says to ignore instructions inside it. Output is validated, and
   everything is rendered as plain text, so nothing the AI writes can become markup.
6. **Line numbers are verified.** The code is shown to the AI with line numbers, and any line the AI cites
   that does not exist in the program is dropped. A final newline does not create an extra line.
7. **Teach, do not give the answer away:** the prompt asks for hints and snippets of at most six lines,
   never a full replacement solution.
8. **Executor independence.** A review reads only data every version of the submission pipeline stores
   (code, language, verdict, counts, compile output, example results). It never runs code and never
   touches an executor, so it works unchanged for submissions produced by Judge0, Piston or the mock.
9. **Access control and cost control.**
   - Sign-in is required, and ownership is part of the query, so someone else's submission looks like a
     missing one (404) and costs no AI call.
   - Only finished submissions that did not fail on our side can be reviewed.
   - Code over 20 000 characters is refused.
   - Reviews are limited to 15 per hour per user, on top of the daily AI quota.
   - A submission is reviewed once (asking again returns the stored review), and simultaneous requests
     share one AI call.
10. **Complexity is labelled an AI estimate.** An AI cannot prove Big-O, so the UI says so.

## Alternatives considered

| Option                                                            | Why not                                                                                               |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Give the AI the hidden tests so it can explain failures           | Risks leaking them through the review text. Counts are enough.                                        |
| Let the AI return the final quality score and correctness verdict | Inconsistent and manipulable; a program that fails tests could be called "correct".                   |
| Review automatically after every submission                       | Costs an AI call each time. On-demand, once per submission, is cheaper and gives the student control. |
| Allow re-reviewing the same submission repeatedly                 | Cost, and different answers each time would be confusing.                                             |
| Render the review as markdown                                     | Adds an injection surface for no benefit.                                                             |

## Consequences

- Good: the feature is bounded, testable without an API key, safe against leaks and manipulation, and
  independent of the code executor.
- Trade-off: a review is only as good as the AI. Ratings other than correctness are subjective, and
  complexity is an estimate.
- Trade-off: the in-flight de-duplication works per server instance; the unique database row still
  guarantees one review if two instances race (the second result is discarded).
- Limitation: the real `AnthropicProvider` has not been run against the live API in development (no
  key was available); the feature is verified with the fake provider.
